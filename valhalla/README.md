# Valhalla

Self-hosted движок маршрутизации ([Valhalla](https://github.com/valhalla/valhalla), образ `valhalla-scripted`): матрицы расстояний и геометрия маршрутов для приложения без квот внешнего OpenRouteService, координаты точек не покидают сеть предприятия. Приложение переключается между движками переменной `ROUTE_ENGINE=ors|valhalla` в своем `.env` и без этого модуля работает на `ors`.

Общих томов с приложением нет, обмен только по HTTP. Для установки приложение не нужно: летний и зимний тайлсеты поднимаются без него, publisher подключается позже, когда появится M2M-токен.

## Состав

| Сервис | Что делает | Адрес из app-network | Снаружи | На хосте |
|---|---|---|---|---|
| `valhalla-summer` | летний тайлсет, поднимается всегда | `valhalla-summer:8002` | `https://<HOST_ROUTE>/summer/` | `127.0.0.1:8002` |
| `valhalla-winter` | зимний тайлсет с зимниками, profile `winter` | `valhalla-winter:8002` | `https://<HOST_ROUTE>/winter/` | `127.0.0.1:8003` |
| `publisher` | публикация кастомных дорог приложения в тайлы | нет | нет | нет |

Контейнеры: `infra_valhalla_summer`, `infra_valhalla_winter`, `infra_valhalla_publisher`. Данные каждого сезона в `custom_files/<сезон>/`: базовая карта, тайлы, конфиг.

## Требования

- Docker с доступом к сети `app-network` (bridge на одном хосте или overlay в swarm, см. корневой README).
- Диск ~20-25 ГБ на тайлсет, пик RAM при сборке ~10-14 ГБ, обслуживание ~1-2 ГБ RAM.
- Для publisher: M2M токен приложения с правами `custom_roads` view и edit.

## Установка

```
cp .env.example .env     # проверить TILE_URLS, остальное можно оставить
./setup.sh               # или ./setup.sh --wait, чтобы дождаться сборки
```

Что делает `setup.sh`, шаг за шагом, каждый пропускается, если уже сделан:

1. `HOST_FILES_DIR` в `.env`: если пусто, записывает каталог `custom_files` рядом со скриптом. На Linux отдает каталог UID 59999, от которого работает образ.
2. Образ publisher: берет локальный, из зеркала `IMAGE_MIRROR` или собирает.
3. Кладет `assets/default_speeds.json` в каталог каждого сезона. Без него образ скачивает файл с GitHub при первой сборке, а в проде GitHub недоступен и сборка падает.
4. Базовая карта: если нет `custom_files/summer/base_map.osm.pbf`, запускает `prepare_pbf.sh summer` (Geofabrik, ~3.5 ГБ, слияние в один файл; несколько PBF образу отдавать нельзя, сборка падает).
5. Поднимает летний сервис. Первая сборка тайлов идет около часа, контейнер в это время unhealthy. Без `--wait` скрипт выходит с подсказкой и продолжает с этого места при следующем запуске.
6. Патчит `valhalla.json` летнего сезона (см. ниже), если патч еще не применен.
7. Наполняет зимний сезон копией летнего и поднимает `--profile winter`.
8. Поднимает publisher, если в `.env` задан `ASU_API_TOKEN`.

Проверка: `curl http://localhost:8002/status`, `curl http://localhost:8003/status`, снаружи `https://<HOST_ROUTE>/summer/status`.

Ручные операции идут через `../compose.sh valhalla ...`, чтобы действовали корневые настройки (`IMAGE_MIRROR`): `../compose.sh valhalla logs -f valhalla-summer`, `../compose.sh valhalla --profile winter ps`.

## Патч valhalla.json

Сгенерированный конфиг содержит четыре фатальных для нас дефолта:

1. `service_limits.*.max_matrix_distance` = 400 км: любая матрица с парой дальше 400 км возвращает 400 Bad Request.
2. `loki.use_connectivity` = true: если хоть одна точка запроса прицепилась к изолированному фрагменту дорог (обычная ситуация для крановых узлов в тундре), весь матричный запрос отклоняется с ошибкой «Locations are in unconnected regions» вместо null для недостижимых пар. Приложение кэширует null как подтвержденно недостижимую пару, поэтому проверку связности отключаем.
3. `thor.costmatrix.allow_second_pass` = false: матрица без второго прохода не проходит шлагбаумы (`barrier=gate`) и участки destination-only. Точка за шлагбаумом дает null в матрице, хотя `/route` для той же пары строит маршрут. Типовая ситуация для подъездов к КУ и ЛПУ.
4. `service_limits.max_radius` = 200 м ограничивает клиентский параметр привязки точки к дорогам.

Патч живет в `publisher/valhalla_config.py`, применяется `setup.sh` после первой сборки и publisher после каждой публикации. Проверка: запрос `/sources_to_targets` с парой дальше 400 км (Москва и СПб) до патча возвращает ошибку, после расстояние. Этой же парой publisher делает смоук-проверку перед вводом нового тайлсета.

## Зимний тайлсет

Приложение запрашивает его при выборе «Сезон дорог: Зима» на страницах прогноза. Кэш расстояний ведется отдельно под ключом `valhalla_winter`.

Без нарисованных зимников зимний граф совпадает с летним, поэтому `setup.sh` наполняет зимний сезон копией летнего каталога целиком, включая `file_hashes.txt` (иначе образ пересобирал бы тайлы час) и пропатченный `valhalla.json`. Зимники добавляются публикацией с `season=winter`, когда приложение поднято и publisher настроен: `./rebuild.sh winter` или заявка из приложения.

## Публикация кастомных дорог

Дороги рисуются в приложении на странице «Кастомные дороги» и публикуются пакетно. Заявка создается кнопкой в UI, дальше все делает publisher:

```
1. Заявка создана в приложении                              status=requested
2. publisher забирает заявку опросом API                    status=preparing
   staging-копия карты, экспорт .osc из API, osmium apply   status=prepared
3. Сборка тайлов одноразовым контейнером, около часа        status=building
4. Патч конфига и смоук-проверка Москва-СПб                 status=finalized
5. Swap каталогов и перезапуск живого сервиса               status=succeeded
```

Живой сервис обслуживает запросы до шага 5, простой это секунды перезапуска. Предыдущее поколение тайлсета остается в `custom_files/<сезон>_prev/`.

Откат: поменять каталоги местами и перезапустить сервис.

```
cd custom_files
mv summer summer_broken && mv summer_prev summer
../../compose.sh valhalla restart valhalla-summer
```

Ручная публикация без заявки: `./rebuild.sh summer`. Делает то же самое, но статусы никуда не пишет.

Логи публикации: `docker logs -f infra_valhalla_publisher`. Упавшая заявка получает статус `failed` с текстом ошибки, который виден в приложении, а staging-каталог остается на диске для разбора.

Builder-контейнер использует образ из `VALHALLA_IMAGE` (с учетом `IMAGE_MIRROR`): на сервере, где образы берутся из зеркала, docker-демон должен быть залогинен в registry (`docker login`).

### Что publisher берет из приложения

| Шаг | Запрос |
|---|---|
| Заявки | `GET /v1/custom-roads/publish-requests?status_filter=requested` |
| Дороги | `GET /v1/custom-roads?active=true&is_deleted=false` |
| Статус | `PATCH /v1/custom-roads/publish-requests/{id}` |

Все запросы с заголовком `Authorization: ApiKey <ASU_API_TOKEN>`. Токен выпускается в приложении на странице «Пользователи и вход», «Токены роли и права», или через API с мастер-ключом. Адрес API задает `ASU_API_URL` в `.env`: при переименовании приложения поменять его.

### HOST_FILES_DIR

Publisher работает в контейнере, но сборку тайлов запускает на docker-демоне хоста. Демон живет вне контейнера publisher и путей внутри него не знает, поэтому том builder'у монтируется по пути **на хосте**. Это и есть `HOST_FILES_DIR`, он должен указывать на тот же каталог `custom_files`, который смонтирован в publisher. `setup.sh` записывает его сам, если переменная пуста.

Если значение разойдется с фактическим, builder получит пустой каталог, отработает час и поднимет пустой граф. Чтобы этого не случилось, publisher перед сборкой проверяет одноразовым контейнером, что карта по хостовому пути видна, и падает сразу с понятной ошибкой.

## Обновление базовой карты

Кастомные дороги при этом не теряются: они хранятся в БД приложения и вливаются заново при следующей публикации.

```
../compose.sh valhalla stop valhalla-summer
rm custom_files/summer/base_map.osm.pbf
./prepare_pbf.sh summer
# в .env временно FORCE_REBUILD=True
../compose.sh valhalla up -d valhalla-summer
# после пересборки вернуть FORCE_REBUILD=False и запустить ./setup.sh: он повторит патч конфига
```

Затем одна публикация, чтобы вернуть кастомные дороги в граф. Зимний сезон обновляется так же или пересозданием: удалить `custom_files/winter` и запустить `./setup.sh`.

## Покрытие карты

7 федеральных округов РФ (СЗФО, ЦФО, ПФО, УрФО, ЮФО, СКФО, СФО), ~3.5 ГБ PBF, ~21 тыс. тайлов. Состав выбран по реальным координатам точек перекачки и ЛПУ в БД, без покрытия остается только Дальний Восток, где точек нет.

Точка, рядом с которой нет ни одной дороги, роняет весь матричный запрос ошибкой сериализатора, поэтому покрытие обязано включать все точки, попадающие в прогноз.

## Бэкап и перенос

Бэкап не требуется: все содержимое `custom_files/` воспроизводится заново, PBF скачиваются, тайлы пересобираются, кастомные дороги лежат в БД приложения. Перенос на новый сервер быстрее сделать копией каталога (`rsync` или `offline/bundle.sh --with-tiles`), чтобы не ждать час сборки.
