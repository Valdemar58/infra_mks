# Valhalla для АСУ ТОиР

Self-hosted движок маршрутизации ([Valhalla](https://github.com/valhalla/valhalla), образ [valhalla-scripted](https://github.com/valhalla/docker-valhalla)): матрицы расстояний и геометрия маршрутов для АСУ ТОиР без квот внешнего OpenRouteService, координаты точек не покидают сеть предприятия.

Живет отдельно от приложения: свой сервер, свой репозиторий. Общих томов с АСУ нет, обмен только по HTTP. Приложение переключается между движками переменной `ROUTE_ENGINE=ors|valhalla` в своем `.env` и без этого модуля полноценно работает на `ors`.

## Состав

| Сервис | Что делает | Адрес из app-network | Порт на хосте |
|---|---|---|---|
| `valhalla-summer` | летний тайлсет, поднимается по умолчанию | `valhalla-summer:8002` | `127.0.0.1:8002` |
| `valhalla-winter` | зимний тайлсет с зимниками, profile `winter` | `valhalla-winter:8002` | `127.0.0.1:8003` |
| `publisher` | публикация кастомных дорог АСУ в тайлы | - | - |

Данные каждого сезона в `custom_files/<сезон>/`: базовая карта, тайлы, конфиг.

## Требования

- Docker с доступом к сети `app-network` (см. «Сеть»).
- Диск ~20-25 ГБ на тайлсет, пик RAM при сборке тайлов ~10-14 ГБ, обслуживание ~1-2 ГБ RAM.
- M2M токен АСУ с правами `custom_roads` view и edit - нужен publisher'у.

## Сеть

Приложение и Valhalla стоят на разных серверах одного swarm, поэтому `app-network` должна быть overlay-сетью, доступной обоим:

```
docker network create -d overlay --attachable app-network
```

`--attachable` позволяет подключать к ней обычные `docker compose` контейнеры, а не только сервисы swarm. Этот стек поднимается именно compose'ом: ему нужны `container_name` (publisher перезапускает живой сервис по имени), `profiles` и bind mount'ы, а `docker stack deploy` ничего из этого не поддерживает. Если стек все же переводить на swarm-сервисы, перезапуск живого сервиса надо будет делать через `docker service update --force`.

Приложение обращается по сетевым алиасам `valhalla-summer` и `valhalla-winter`, а не по `container_name`, поэтому имя стека можно менять, не трогая `.env` приложения. Порты на хост открыты только на `127.0.0.1` - наружу сервис не смотрит, nginx его не проксирует.

## Первый запуск

На Linux каталог данных должен принадлежать UID 59999, от которого работает образ:

```
mkdir -p custom_files/summer && sudo chown -R 59999:59999 custom_files
```

Дальше:

```
cp .env.example .env       # заполнить ASU_API_TOKEN и HOST_FILES_DIR
./prepare_pbf.sh summer    # скачивает выгрузки Geofabrik (~3.5 ГБ) и сливает в base_map.osm.pbf
docker compose up -d
```

`prepare_pbf.sh` обязателен: контейнеру всегда передается **один** PBF-файл. Сборка тайлов из нескольких PBF, лежащих в каталоге, нестабильна и падает (`valhalla_build_tiles ... Aborted (core dumped)`), после чего сервис поднимается с пустым графом и на все запросы отвечает `No suitable edges near location`.

Первая сборка тайлов занимает около часа, контейнер в это время unhealthy - это норма. Прогресс: `docker logs -f asu_toir_valhalla_summer`. Проверка после сборки: `curl http://localhost:8002/status`.

**После первой сборки обязателен патч конфига** (при публикации через publisher он применяется сам):

```
docker compose exec publisher python -m publisher.cli patch-config /custom_files/summer/valhalla.json
docker compose restart valhalla-summer
```

## Патч valhalla.json

Сгенерированный конфиг содержит четыре фатальных для нас дефолта:

1. `service_limits.*.max_matrix_distance` = 400 км - любая матрица с парой дальше 400 км возвращает 400 Bad Request.
2. `loki.use_connectivity` = true - если хоть одна точка запроса прицепилась к изолированному фрагменту дорог (обычная ситуация для крановых узлов в тундре), весь матричный запрос отклоняется с ошибкой «Locations are in unconnected regions» вместо null для недостижимых пар. Приложение кэширует null как подтвержденно недостижимую пару, поэтому проверку связности отключаем.
3. `thor.costmatrix.allow_second_pass` = false - матрица без второго прохода не проходит шлагбаумы (`barrier=gate`) и участки destination-only. Точка за шлагбаумом дает null в матрице, хотя `/route` для той же пары строит маршрут: у него второй проход включен всегда. Типовая ситуация для подъездов к КУ и ЛПУ.
4. `service_limits.max_radius` = 200 м ограничивает клиентский параметр привязки точки к дорогам.

Патч живет в `publisher/valhalla_config.py` и применяется после каждой сборки тайлов. Проверка: запрос `/sources_to_targets` с парой дальше 400 км (Москва - СПб) до патча возвращает ошибку, после - расстояние. Именно этой парой publisher делает смоук-проверку перед вводом нового тайлсета.

## Публикация кастомных дорог

Дороги рисуются в АСУ на странице «Кастомные дороги» и публикуются пакетно. Заявка создается кнопкой в UI, дальше все делает publisher:

```
1. Заявка создана в АСУ                                    status=requested
2. publisher забирает заявку опросом API                   status=preparing
   staging-копия карты, экспорт .osc из API, osmium apply  status=prepared
3. Сборка тайлов одноразовым контейнером, около часа       status=building
4. Патч конфига и смоук-проверка Москва-СПб                status=finalized
5. Swap каталогов и перезапуск живого сервиса              status=succeeded
```

Живой сервис обслуживает запросы до шага 5, простой - секунды перезапуска. Предыдущее поколение тайлсета остается в `custom_files/<сезон>_prev/`.

Откат: поменять каталоги местами и перезапустить сервис.

```
cd custom_files
mv summer summer_broken && mv summer_prev summer
docker compose restart valhalla-summer
```

Ручная публикация без заявки: `./rebuild.sh summer`. Делает ровно то же самое, но статусы никуда не пишет.

Логи публикации: `docker logs -f asu_toir_valhalla_publisher`. Упавшая заявка получает статус `failed` с текстом ошибки, который виден в АСУ, а staging-каталог остается на диске для разбора.

### Что publisher берет из АСУ

| Шаг | Запрос |
|---|---|
| Заявки | `GET /v1/custom-roads/publish-requests?status_filter=requested` |
| Дороги | `GET /v1/custom-roads?active=true&is_deleted=false` |
| Статус | `PATCH /v1/custom-roads/publish-requests/{id}` |

Все запросы с заголовком `Authorization: ApiKey <ASU_API_TOKEN>`. Токен выпускается в АСУ на странице «Пользователи и вход» -> «Токены роли и права» или через API с мастер-ключом.

### HOST_FILES_DIR

Publisher работает в контейнере, но сборку тайлов запускает на docker-демоне хоста. Демон живет вне контейнера publisher и путей внутри него не знает, поэтому том builder'у монтируется по пути **на хосте** - это и есть `HOST_FILES_DIR`. Он должен указывать на тот же каталог `custom_files`, который смонтирован в publisher.

Если значение разойдется с фактическим, builder получит пустой каталог, отработает час и поднимет пустой граф. Чтобы этого не случилось, publisher перед сборкой проверяет одноразовым контейнером, что карта по хостовому пути видна, и падает сразу с понятной ошибкой.

## Зимний тайлсет

Приложение запрашивает его при выборе «Сезон дорог: Зима» на страницах прогноза. Кэш расстояний ведется отдельно под ключом `valhalla_winter`.

Первый запуск:

```
cp custom_files/summer/base_map.osm.pbf custom_files/winter/   # базовая карта общая
./rebuild.sh winter        # экспорт дорог season in (all, winter) + сборка + патч + swap
docker compose --profile winter up -d
```

Без нарисованных зимников зимний граф совпадает с летним - это нормальный первый шаг. Зимники добавляются публикацией с `season=winter`.

## Обновление базовой карты

Кастомные дороги при этом не теряются: они хранятся в БД АСУ и вливаются заново при следующей публикации.

```
docker compose stop valhalla-summer
rm custom_files/summer/base_map.osm.pbf
./prepare_pbf.sh summer
# в .env временно FORCE_REBUILD=True
docker compose up -d valhalla-summer
# после пересборки вернуть FORCE_REBUILD=False и повторить патч конфига
```

Затем одна публикация, чтобы вернуть кастомные дороги в граф.

## Покрытие карты

7 федеральных округов РФ (СЗФО, ЦФО, ПФО, УрФО, ЮФО, СКФО, СФО), ~3.5 ГБ PBF, ~21 тыс. тайлов. Состав выбран по реальным координатам точек перекачки и ЛПУ в БД, без покрытия остается только Дальний Восток, где точек нет.

Точка, рядом с которой нет ни одной дороги, роняет весь матричный запрос ошибкой сериализатора, поэтому покрытие обязано включать все точки, попадающие в прогноз.

## Бэкап

Не требуется: все содержимое `custom_files/` воспроизводится заново - PBF скачиваются, тайлы пересобираются, кастомные дороги лежат в БД АСУ. Перенос на новый сервер быстрее сделать копией каталога (`rsync`), чтобы не ждать час сборки.
